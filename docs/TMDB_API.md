# TMDB для AbsoluteCinema

Документация изучена 8 октября 2026 года. Это предложение подключения; текущий dev продолжает работать на моках.
Источник — официальная [API Reference v3](https://developer.themoviedb.org/reference/getting-started).

## Минимальный набор запросов

Базовый адрес: `https://api.themoviedb.org/3`. Все методы ниже используют GET.

| Эндпоинт | Применение в приложении | Параметры первого варианта |
| --- | --- | --- |
| [/search/movie](https://developer.themoviedb.org/reference/search-movie) | Поиск фильмов по названию | `query`, `language=ru-RU`, `include_adult=false`, `page=1` |
| [/movie/{movie_id}](https://developer.themoviedb.org/reference/movie-details) | Загрузка карточки выбранного фильма | ID из результатов поиска, `language=ru-RU` |
| [/movie/popular](https://developer.themoviedb.org/reference/movie-popular-list) | Начальный список, пока пользователь ничего не ищет | `language=ru-RU`, `page=1` |

Первыми достаточно подключить поиск и карточку. Популярные фильмы добавляют полезное начальное содержимое без отдельной модели рекомендаций.
Начальную версию поиска можно запускать кнопкой или отправкой введённого текста.

В карточке потребуются поля `id`, `title`, `original_title`, `release_date`, `runtime`, `overview`, `genres`, `vote_average`, `vote_count`, `poster_path`.
Ответ спискового запроса оборачивает фильмы в `results`; краткие результаты нельзя считать полной карточкой с длительностью и названиями жанров.
При подключении описать JSON через небольшие Decodable-структуры и преобразовать их в модель фильма.
Пустую дату, описание или отсутствующий постер обрабатывать как допустимый ответ.
Структуру ответов нужно сверить с официальной схемой и одним ответом API при подключении; в этом шаге запросы с личным ключом не выполнялись.

## Постеры

TMDB возвращает `poster_path`, а полный адрес собирается из адреса изображений, размера и пути.
[/configuration](https://developer.themoviedb.org/reference/configuration-details) сообщает допустимые размеры и базовый адрес изображений.
В официальном [примере](https://developer.themoviedb.org/docs/image-basics) используется `https://image.tmdb.org/t/p/w500` с добавленным `poster_path`.
Для маленькой строки списка можно использовать меньший доступный размер, для карточки — w500; заглушку текущего MoviePoster сохранить.

Для подключения сети модель фильма потребуется дополнить путём или URL постера: сейчас `posterName` обозначает локальный asset.

## Авторизация приложения

TMDB v3 поддерживает два варианта с одинаковым уровнем доступа: API Key в параметре `api_key` или API Read Access Token в заголовке `Authorization: Bearer …`.
Их нельзя подменять друг другом. Подробности — в [Application Authentication](https://developer.themoviedb.org/docs/authentication-application).

У разработчика есть ключ. В репозитории локальный Configuration/TMDBConfig.plist игнорируется Git и исключён из текущей сборки dev.
При подключении проверить чтение локальной конфигурации и включение нужного ресурса в сборку. Наличие файла сейчас не означает, что API подключён.

## Оценки и «Хочу посмотреть»

Предлагаю использовать TMDB для чтения данных, а личную оценку, комментарий и список желаемого сохранять в SwiftData по ID фильма.
Так действия карточки напрямую демонстрируют работу с локальным хранением.

У TMDB также есть [POST /movie/{movie_id}/rating](https://developer.themoviedb.org/reference/movie-add-rating), работающий с пользовательской или гостевой сессией,
и [POST /account/{account_id}/watchlist](https://developer.themoviedb.org/reference/account-add-to-watchlist) для списка аккаунта.
Это отдельный вариант синхронизации с TMDB, который добавляет работу с сессиями. В минимальный прототип его пока не включаем.

Списки оценок и желаемого уже передают в карточку сохранённые сведения Movie; ContentView не ищет их повторно в MockMovies.
При подключении API нужно сохранить этот путь открытия локального фильма.

## Возможный пример для занятия

Дополнительный [GET /movie/{movie_id}/recommendations](https://developer.themoviedb.org/reference/movie-recommendations) возвращает рекомендации для фильма.
Он пригодится, если понадобится блок рекомендаций или понятный пример конкурентной загрузки.

При уже известном ID запрос деталей и запрос рекомендаций могут выполняться независимо.
Если преподавателю подходит Swift Concurrency, можно показать два запроса через `async let` и обновление состояния экрана на MainActor.
Это предложение, выбор механизма ещё не согласован. Для базового прототипа рекомендации необязательны.

Асинхронность позволяет приостанавливать ожидание; она сама по себе не гарантирует выполнение кода на отдельном потоке.
`async let` запускает дочерние задачи, которые могут выполняться конкурентно. Подробности — в официальной [главе Swift о concurrency](https://github.com/swiftlang/swift-book/blob/main/TSPL.docc/LanguageGuide/Concurrency.md).
Текущий @MainActor в ViewModel и репозитории ограничивает доступ к их состоянию; это ещё не реализованный пример фоновой работы.
